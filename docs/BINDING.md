# Binding manifest v1

The optional manifest binds a basis file, an rdiff delta, and expected result bytes. It is a separate JSON document and changes no rdiff wire bytes. The schema is:

```json
{
  "schema_version": 1,
  "algorithm": "blake2b-256",
  "basis": {"size": 0, "hash": "0e5751c026e543b2e8ab2eb06099daa1d1e5df47778f7787faab45cdf12fe3a8"},
  "target": {"size": 0, "hash": "0e5751c026e543b2e8ab2eb06099daa1d1e5df47778f7787faab45cdf12fe3a8"},
  "delta": {"size": 0, "hash": "0e5751c026e543b2e8ab2eb06099daa1d1e5df47778f7787faab45cdf12fe3a8"}
}
```

The example shows file identity syntax, not a usable update: an empty delta is invalid. Hash is standard unkeyed BLAKE2b with a 32-byte output, lowercase hex; sizes are nonnegative Int32 bytes. Root and identity objects require exactly the shown keys. Duplicate keys, unsupported algorithms/versions, malformed UTF-8, invalid hashes, unknown fields and manifests above 16 KiB are rejected.

`manifest BASIS TARGET DELTA OUTPUT` hashes the three regular files in bounded chunks and creates a new document exclusively. It records an association without asserting that the patch is valid for that target. All three files must be available at creation; a distributed metadata exchange is not implemented.

`patch ... --manifest FILE` first verifies basis/delta sizes and full digests, then preflights the patch while hashing reconstructed bytes and the patch bytes consumed. No output is created unless the reconstruction matches target size/digest and the patch digest matches. The second pass hashes those streams again and reports success only on a match. This checks generated bytes passed to file writes; it is not an independent post-write disk readback. IO and final sync failures still produce errors.

The manifest does not contain executable commands, file paths to open, or a digital signature. It must be obtained from a trusted source; an attacker able to replace both patch and manifest can choose a different expected update. These checks detect mismatched versions or corruption, not publisher identity. Input files must remain stable: size rechecks and stream hashes are not filesystem snapshots. Same-size concurrent changes, storage failures and atomic publishing remain outside a transactional guarantee. Published 0.1.2 can leave a new partial output file after write failure. The current development CLI instead retains data in a same-parent staging directory and publishes only after writer checks/sync/close, using no-replace rename; success JSON follows publication. A post-publication cleanup/output failure still exits 2 and explicitly reports that publication already occurred. See CLI.md for the staging contract and filesystem limitations. Existing outputs are always refused.

The incremental BLAKE2 adapter retains the attributed Apache-2.0 compression core and tests exact block sizes against independent Python hashlib vectors. File acceptance additionally compares generated manifest digests with Python and rejects both same-size modified input and truthful but unrelated target associations.
